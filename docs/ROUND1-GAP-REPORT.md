## 二、两个未达成项的定量根因

### 2.1 第 6 条：pass@1 训练前后全为 0

`results/comparison.md` 实测：

| 指标 | 训练前 | 训练后 | 变化 |
|---|---|---|---|
| pass@1 (strict) | 0.0000 | 0.0000 | +0.0000 |
| pass@1 (partial) | 0.0000 | 0.0000 | +0.0000 |
| **patch 可应用率** | **0.0000** | **0.0000** | +0.0000 |
| 平均 reward | 0.0000 | 0.0000 | +0.0000 |

逐题明细 4 题（`swe-synth-0015/0018/0020/0022`）全为 `False`。

**注意 `patch 可应用率 = 0`** —— 模型在评测集上**一个能应用的 patch 都没产出**，
根本没走到"测试是否通过"这一步。所以 pass@1 为 0 不是"修不对"，是"写不出合法 patch"。

**根因一：任务表示要求模型手算 diff 行号**

项目 `README §7` 记录的 440 次采样失败分布：

| 失败原因 | 次数 |
|---|---|
| `corrupt patch at line N` | **227** |
| `patch fragment without header` | 44 |
| `patch does not apply` | 10 |

strict 模式可应用率 **8/440 = 1.8%**。

unified diff 要求模型手工计算 hunk header（`@@ -起始行,行数 +起始行,行数 @@`），
这对 1.5B 模型是硬伤 —— 一位算错整个 patch 作废。**这不是"不会修 bug"，是"不会算数"。**

**根因二：评测规模不足，无统计功效**

评测集 4 题 × k=1 = **4 个样本**。按 strict 成功率 1.8% 估算，
期望成功次数 = 4 × 0.018 = **0.07** —— 结果必然全 0。
Welch t 检验 `t = −0.22`，完全不显著。

即便模型真有提升，这个规模也测不出来。

### 2.2 第 4 条：reward 曲线 U 型不上升

`docs/reward_curve.csv` 实测（55 step）：

| 分段 | reward 均值 |
|---|---|
| 前 1/3 | 0.0722 |
| 中 1/3 | 0.0835 |
| 后 1/3 | 0.0625 |

**关键分布特征**：

| 项 | 数据 |
|---|---|
| 全程均值 | 0.0728 |
| **均值 ≤ 0.2 的 step** | **54 / 55** |
| **均值 > 0.2 的 step** | **1 / 55**（step 47，0.225） |
| 组内出现满分（max=1.0）的 step | 1 / 55（step 47） |

分数集中在 `0.05 / 0.075 / 0.1 / 0.125 / 0.15`，这些是"8 个采样里 1~4 个拿到 0.2、
其余为 0"的组内平均值。

**→ 模型全程几乎只拿到「patch 能被 git apply」的格式分（0.2），
从未从「真正修对题」获得有效信号。**

**根因：reward 分档过粗，把两类本质不同的样本混为一谈**

```
apply 成功 + 位置正确 + 测试可收集   → 0.2
apply 成功 + 插错位置 + 代码语法坏   → 0.2      ← 实测占 apply 成功的 51%
```

`collect_error` 稳定占 apply 成功的 **51%**（两个独立时间点分别为 50%、51%，
属结构性而非随机波动）。组内 advantage 因此无法区分"写歪"与"写对"，
等于告诉模型"两者一样值钱" —— 格式能力自然学不动。

## 三、两项架构性偏差（比上面两条更需优先修复）

这两项是课题**技术要求**中明确写明的，第一轮的实现均有偏差。

### 3.1 沙箱与 GPU 跨地域，未走 VPC 内网

实测配置：

| 组件 | 地域 |
|---|---|
| AGS 沙箱（`E2B_DOMAIN=ap-shanghai.tencentags.com`） | **ap-shanghai** |
| TKE GPU 集群 | **ap-beijing** |

**跨地域 VPC 天然不通。**

`deploy/gpu-pod.yaml` 中沙箱访问推理服务的方式：

```yaml
kind: Service
metadata:
  name: swe-rl-llm
spec:
  type: LoadBalancer     # ← 申请公网 CLB
  ports:
    - port: 8000
```

即：**上海的沙箱通过公网 CLB 访问北京的 GPU 推理服务**。

课题要求沙箱网络类型使用 **VPC**（走内网打通），而当前用的是默认的
`SANDBOX` 网络类型 + 公网暴露。功能上能跑通，但不符合要求，且暴露面大。

**修复方向（三选一）**：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 把 GPU 节点迁到 **ap-shanghai**，与沙箱同地域同 VPC，沙箱改用 VPC 网络类型直连内网 | 需在上海重开 GPU 节点、重传权重与镜像 |
| B | 用 **CCN 云联网**打通京沪两个 VPC | 跨地域带宽需单独付费；延迟约 30ms，每步 8~16 次打分会累积 |
| C | 若 AGS 支持 ap-beijing，把沙箱迁到北京 | 最省事，仅需重建沙箱工具；需先确认 AGS 地域支持 |

> 沙箱工具配额若已满（如 10/10），新建 VPC 类型工具前需先删除一个旧工具。

### 3.2 训练部署方式（第一轮此项**正确**，仅作对照记录）

第一轮 `deploy/gpu-pod.yaml` 是标准 k8s Pod（`kind: Pod`，`nvidia.com/gpu: 1`），
由 kubelet 调度到 TKE GPU 节点 —— **符合课题「在 TKE GPU 节点上部署 VERL」的要求。**

> 对照：第二轮项目（`swe-rl-verified`）改用宿主机 `ctr` 直起容器、绕过 k8s，
> **这一项反而是退步**，需改回 Pod 部署。

**但第一轮的 Pod 定义有一个数据安全缺陷需修复**：

`/workspace` 未挂载 hostPath，模型权重（2.9G）与 checkpoint（22G）全在容器可写层，
**删除 Pod 即全部丢失**。建议改为挂载宿主机目录：

```yaml
volumeMounts:
  - name: workdir
    mountPath: /workspace
volumes:
  - name: workdir
    hostPath:
      path: /data/swe-rl
      type: DirectoryOrCreate
```

## 四、修复建议（按性价比排序）

### 优先级 1：改任务表示为 search/replace（直击根因一）

不要让模型写 unified diff，改为：

```
### path/to/file.py
<<<<<<< SEARCH
    原始代码片段（逐字匹配）
=======
    替换后的代码
>>>>>>> REPLACE
```

**完全不需要行号** —— 靠内容定位，行号由程序用 `difflib` 确定性算出。
把"算数"这项与修复能力无关的负担从模型身上卸掉。

> **第二轮已实测此改动的效果**：
> 「写了但打不进代码库」从第一轮的 **227 次** 降到 **1 次**；
> 组内出现满分的 step 占比从 **1.8%** 升到 **22.6%**（且题目难度更高 ——
> 第二轮用的是 SWE-bench Verified 真实开源项目 issue，第一轮是自建合成题）。
>
> 可直接参考第二轮实现：`pipeline/edit_format.py`（含 8 项自测）。

需要配套：在 prompt 中**嵌入待修改文件的真实内容**（模型需要"看见"代码才能引用片段），
并把文件路径以固定清单给出（第一轮实测存在路径幻觉：丢 `src/` 前缀、凭空加 `jd/` 前缀）。

### 优先级 2：reward 分档细化（直击根因二）

现有 2 档 → 4 档：

| 档位 | 条件 |
|---|---|
| `0.00` | 没写出 patch / apply 失败 |
| **`0.05`** | apply 成功但 `collect_error`（代码被插坏）← **新增** |
| `0.20` | apply 成功且测试可正常收集 |
| `0.20 + 0.80 × F2P通过率` | 真修对 |

让"写歪"与"写对"产生 **4 倍**差距，组内 advantage 才能推动格式能力改进。

> 参考实现：第二轮 `pipeline/reward.py`（含 13 项自测），
> 同时保留了防 reward hacking（P2P 回归即判 0）。

### 优先级 3：扩大评测规模（解决第 6 条的统计功效）

当前 4 题 × k=1 = 4 样本 → 建议 **≥10 题 × k=8 = 80 样本**。

样本数决定能否检出提升：4 样本下期望成功次数 0.07，注定全 0；
80 样本的相对标准误比 4 样本方案降约 37%。

报告需附显著性检验（第一轮已有 Welch t 检验的做法，保留即可）。

### 优先级 4：修网络架构（第 3.1 节）

按方案 A/B/C 三选一。若时间紧张，至少在 README 中如实说明当前是公网通路、
并记录跨地域 VPC 不通的客观限制。

### 优先级 5：提高单步信噪比

第一轮 `train_batch_size=1`，使单步 reward 主要由"抽到哪道题"决定，而非策略好坏。

> **第二轮踩过的坑，可直接避开**：第二轮把 `train_batch_size` 改为 2，
> 结果 63 行数据只跑出 31 step（行数被折半），反而不满足 ≥50 step。
> 正确做法是保持 `train_batch_size=1`，改为**加大 `rollout.n`（8 → 16）**
> 来减少「组内 8 个采样全 0 分 → advantage 恒 0 → 无梯度」的步。
>
> 第二轮实测 **14/31 步** 出现该情况，是曲线难看的直接原因。
>
> 更根本的是**扩大题池**：第二轮只用 9 题，单步抽样方差压过学习信号，
> 满分步完全随机散布（step 2,7,9,11,20,25,29），无收敛特征。
> 题池建议 ≥20 题。

### 一个值得特别提醒的坑

AGS 首次使用新推送的镜像时会报：

```
FailedOperation.ImagePrepare: Internal server error
```

**这不是故障，只是镜像预热未完成，等约 4 分钟即可。**
第二轮曾据此误判为"镜像清单格式不被平台接受"，白改了两版镜像融合方案。
真实提示是 `ResourceUnavailable: image is still preparing, please retry later`。

第二轮另外三个已定位的坑：

| 现象 | 真因 |
|---|---|
| `ContainerStart: init command path error` | 官方 SWE-bench 镜像缺 AGS 的 envd agent，需用 `docker build` 多阶段 COPY 注入 envd + s6-overlay |
| `AuthenticationException: unknown user 'user'` | 官方镜像无 `user` 账号，e2b SDK 默认以该身份写文件 → 需显式 `user="root"` |
| `future feature annotations is not defined` | 题目 conda 环境可能老至 py3.6。判据脚本应用 `/usr/bin/python3`(3.10) 执行、内部调 testbed python 跑 pytest；**必须写绝对路径**，否则 PATH 中 conda 在前会解析错解释器 |
